# אפיון: שקים חוזרים וסגירת המעגל תזכורת-תקבול

> נוצר 2026-07-26 בעקבות brainstorming עם אמיר.

## הבעיה

אמיר סימן תזכורת "הפקדת שק שכ"ד - שלומציון המלכה 5 - יולי 2026" כבוצעה, והתקבול נשאר פתוח.

חקירה בקוד ובדאטה הראתה שהקישור בין המסכים **חד-כיווני**:

- **תקבול לתזכורת** - עובד. `PUT /api/payments/[id]` קורא ל-`closeCheckReminderForPayment`.
- **תזכורת לתקבול** - לא קיים. `PUT /api/tasks/[id]` מעדכן `completed_at` בלבד.

ראיות מהדאטה: המשימה שנסגרה ב-25.7.2026 בשעה 21:08:30 **נוצרה באותה שנייה** (כלומר הייתה וירטואלית עד ללחיצה), עם `source_payment_id` ריק, ובלי שקיימת שורת תקבול כלשהי לשלומציון ליולי 2026.

**באג משני שנחשף באותה חקירה:** אם יסמן עכשיו את התקבול, `closeCheckReminderForPayment` יחפש משימה **פתוחה** לאותו חוזה+חודש, לא ימצא (היא כבר סגורה), וייצור שורה שנייה - שתי תזכורות כפולות לאותו חודש.

**דרישה נוספת** שעלתה בשיחה: כשמסמנים שק כמשולם וחוזר בהמשך מהבנק, צריך לתעד זאת כאירוע משמעותי - "חיווי שק חזר הרבה יותר משמעותי מתשלום שלא שולם ולא כדאי להתייחס לכך בצורה שווה".

## המטרה

1. סימון תזכורת הפקדת שק כבוצעה **ירשום את התקבול** כשולם.
2. לא ייווצרו תזכורות כפולות באף כיוון.
3. שק שחזר מתועד כאירוע נפרד, בולט יותר מחוב רגיל, עם **שרשרת מלאה** של החזרות חוזרות לצורך פנייה לעורך דין.

## מודל הנתונים

טבלה חדשה `check_bounces`. **אירוע** ולא סטטוס - כך שרשרת החזרות נשמרת במלואה.

<div dir="rtl" align="right">

| שדה | טיפוס | הערה |
|---|---|---|
| `id` | text PK | `gen_random_uuid()::text`, כמו שאר הטבלאות |
| `user_id` | uuid | FK ל-`auth.users`, `on delete cascade` |
| `payment_id` | text | FK ל-`payments`, **`on delete set null`** - ההיסטוריה שורדת מחיקת תקבול |
| `lease_id` | text | FK ל-`leases`, `on delete cascade`. משוכפל בכוונה - מאפשר שליפת השרשרת גם אם התקבול נמחק |
| `bounced_at` | timestamptz | תאריך ההחזרה שהמשתמש הזין |
| `reason` | text | `nsf` \| `restricted` \| `cancelled` \| `other` |
| `created_at` | timestamptz | `default now()` |

</div>

RLS: `create policy "check_bounces_owner" on check_bounces for all using (user_id = auth.uid())` - זהה לדפוס בשאר הטבלאות.

**אין** עמודות חדשות על `payments`. המצב נגזר:

<div dir="rtl" align="right">

| מושג | הגדרה |
|---|---|
| לתקבול חזר שק אי-פעם | קיימת לו לפחות שורת `check_bounces` אחת |

## שינויים בקוד

### 1. סימון תזכורת יוצר את התקבול

ב-[tasks/page.tsx](../../../src/app/dashboard/tasks/page.tsx), `complete(t)` מזהה תזכורת הפקדת שק (`category === "Rent Collection"` וגם `related_entity_type === "lease"`) ומנתב אותה דרך **ה-API של התקבולים** במקום לעדכן את המשימה ישירות:

1. מחפש שורת תקבול קיימת לאותו חוזה+חודש.
2. קיימת - `PUT /api/payments/[id]` עם `{ status: "paid", paid_date: now }`.
3. לא קיימת (התזכורת הייתה וירטואלית) - `POST /api/payments` עם `payment_type: "Rent"`, סכום `monthly_rent` של החוזה, `due_date` של אותו חודש, `status: "paid"`, `paid_date: now`.

הניתוב הזה הוא לב התיקון: `closeCheckReminderForPayment` שכבר רץ בשני המסלולים סוגר את המשימה **ומקשר** אותה דרך `source_payment_id`. הלקוח לא צריך לעדכן את המשימה בעצמו, ומצב של תזכורת סגורה בלי תקבול הופך לבלתי-אפשרי.

`closeCheckReminderForPayment` יקבל פרמטר `title` אופציונלי, כדי שמשימה שנוצרת מתזכורת וירטואלית תשמור על הכותרת המלאה (`הפקדת שק שכ"ד - נורדאו 58, תל אביב - יולי 2026`) במקום הכותרת הגנרית.

תזכורות שאינן הפקדת שק (חשבונות שירות, חידוש חוזה) ממשיכות במסלול הקיים ללא שינוי.

**תנאי סף שאסור לשבור:** שני נתיבי התקבולים מפעילים את `closeCheckReminderForPayment` רק כאשר `payment_type = "Rent"`, `status = "paid"` **מלא** (לא חלקי), ו-`isCheckPaymentMethod(lease.payment_method)`. זה עקבי עם `generateVirtualCheckTasks` שממילא מייצר תזכורות רק לחוזים בשיטת תשלום שקים. תשלום **חלקי** לא סוגר תזכורת ולא נחשב הפקדה - ולכן גם לא ניתן לסמן עליו שק שחזר.

### 2. תיקון הכפילות

ב-[check-reminders.ts](../../../src/lib/check-reminders.ts), `closeCheckReminderForPayment` מקבל שלב חיפוש נוסף לפני היצירה:

1. משימה עם `source_payment_id` תואם - קיים היום.
2. משימה **פתוחה** לאותו חוזה+חודש - קיים היום.
3. **חדש:** משימה **סגורה** לאותו חוזה+חודש שאין לה `source_payment_id` - מאמץ אותה (מעדכן `source_payment_id` בלבד, `completed_at` נשאר).
4. רק אם אף אחד מהשלושה - יוצר שורה חדשה.

שלב 3 הוא שמונע את הכפילות במקרה של אמיר, וגם בכל מקרה עתידי שבו המשתמש סימן קודם בתזכורות.

### 3. סימון שק שחזר

ראוט חדש `POST /api/payments/[id]/bounce`, גוף `{ bounced_at, reason }`:

1. ולידציה: התקבול שייך למשתמש, ו-`status === "paid"` (אי אפשר להחזיר שק שלא הופקד).
2. `insert` ל-`check_bounces` עם `payment_id`, `lease_id` מהתקבול, והשדות מהגוף.
3. `update payments` - `status: "pending"`, `paid_date: null`.
4. `reconcileAutoTax` - `getReceivedAmount` יחזיר 0 ולכן הוצאת המס האוטומטית **נמחקת מעצמה**.
5. `reopenCheckReminderForPayment` - תזכורת ההפקדה נפתחת מחדש.

שלבים 4-5 הם קריאות לקוד קיים. זו הסיבה המרכזית לבחירת מודל שבו שק שחזר מחזיר את הסטטוס ל-`pending`: כל ההשלכות (מס, הכנסה בדוחות, תזרים, חוב פתוח) נגזרות מ-`getReceivedAmount` וקורות ללא שינוי בהן.

ראוט קריאה `GET /api/check-bounces` מחזיר את כל השורות של המשתמש (טבלה קטנה), בדפוס של `/api/index-rates`.

### 4. מודול דומיין טהור

קובץ חדש `src/lib/domain/check-bounce.ts` - פונקציות טהורות, ניתנות לבדיקה בלי DB:

```ts
export type BounceReason = "nsf" | "restricted" | "cancelled" | "other";
export const BOUNCE_REASON_LABELS: Record<BounceReason, string>;

/** האם לתקבול יש שק שחזר וטרם טופל. מקבל את כל השורות ומסנן לפי id בעצמו */
export function hasOpenBounce(payment: { id: string; status: string }, bounces: CheckBounce[]): boolean;

/** שרשרת ההחזרות של תקבול, מהישן לחדש - התצוגה לעו"ד */
export function bounceChainForPayment(paymentId: string, bounces: CheckBounce[]): CheckBounce[];

/** אורך השרשרת בחוזה - סופר אירועים, לא תקבולים */
export function bounceCountForLease(leaseId: string, bounces: CheckBounce[]): number;
```

## ממשק משתמש

### דשבורד - דורש טיפול

ב-[attention.ts](../../../src/lib/domain/attention.ts) נוסף `kind: "bounced"` ל-`AttentionItem`, וקלט חדש `bounces` ל-`buildAttentionItems`. פריטי שק שחזר ממוינים **ראשונים**, לפני חובות וחוזים שמסתיימים.

צבע: rose/אדום מלא (`text-rose-700`), לא כתום - נבדל מ"פג מועד" הרגיל, לפי ההנחיה שלא להתייחס לשניהם באותה צורה.

תווית: `שק חזר - שלומציון המלכה 5` · תת-שורה: `₪5,500 · אכ"מ · 26.7.2026`

### מסך תקבולים

מקטע חדש **מעל** מקטע "לתשלום", בעקבות ההעדפה המתועדת ל-sections נפרדים על פני סינון. מוצג רק כשיש שקים שחזרו וטרם טופלו.

כותרת: `שקים שחזרו (2)`, כרטיס בגוון rose.

## מה מחוץ לגבולות

- **עמלת בנק** על החזרת שק - נדחה במפורש.
- **התראת Push** - נדחה במפורש.
- **פינוי וביטול חוזה** בשל שקים חוזרים - נושא נפרד, בסשן עתידי. הפער שזוהה: הראוט הקיים `POST /api/leases/[id]/terminate` מניח עזיבה **מוסכמת** עם חודשי הודעה, ו-`early_term_protection` יחסום ביטול בשל הפרה. השרשרת שנבנית כאן היא הקלט לאותו תהליך.
- **חילוט בטחונות** לכיסוי שק שחזר - נושא נפרד באותו סשן עתידי.
